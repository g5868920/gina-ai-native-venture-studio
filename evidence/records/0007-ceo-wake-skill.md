## Decision Provenance (per CLAUDE.md)

1. **Before state:** Waking the Studio AI CEO in a fresh session required pasting the full new-session recovery instruction from `docs/OPERATING_LOOP.md` §5 / Step 14 by hand each time. The three Decision 0007 §7 S6 skill adapters (`decision-packet`, `portfolio-review`, `consulting-proposal-review`) existed under `.claude/skills/`, committed at `7722ddb`; no one-command wake trigger existed. Repo was `main` @ `7722ddb`, clean, synced with `origin/main`.

2. **Problem and constraints:** Gina wanted a single trigger (`/ceo`) to wake the CEO from any Chat, Cowork, or Code session without re-explaining context, and to have the CEO consult the other executive functions and bring back synthesized recommendations. Constraints: must grant no new authority; must not create a new decision or claim Chairwoman approval; must stay subordinate to `CLAUDE.md` and `docs/OPERATING_LOOP.md`; must inherit all existing governance boundaries (reserved decisions, single-writer, Git boundaries, product-repo read-only, surface-conflicts); executive invocation must follow `executives/HANDOFF_RULES.md` and preserve activation states.

3. **Options considered:** (a) keep pasting the recovery prompt manually — declined (the point was one-command wake); (b) account-level Claude skill only — usable in Chat/Cowork but not version-controlled or portable to Code; (c) repo `.claude/skills/ceo/SKILL.md` adapter only — version-controlled and works in Code, but not present as an uploaded skill in Chat/Cowork sessions that are not opened on the repo; (d) **selected:** both — an account skill (installed via a delivered `.skill` file) plus a version-controlled repo adapter, with this evidence record for provenance. Separately considered and **declined**: building per-executive wake commands (`/cpo`, `/cto`, `/cbo`). Gina chose the governance-cleaner path of having the single CEO route to executive functions per `HANDOFF_RULES.md` §1, which keeps the single-entry CEO-routing model and avoids per-executive personas; the `/ceo` skill was instead enhanced with an explicit routing section.

4. **Decision and rationale:** The `/ceo` skill is a tooling-layer operationalization of S1 (`docs/OPERATING_LOOP.md`) plus the already-approved CEO routing behavior in `executives/HANDOFF_RULES.md` — not a new capability or authority. It is **not** one of Decision 0007 §7 S6's three named adapters and does not claim to be; it is added at Chairwoman direction (2026-07-14) under the same non-canonical, no-new-authority pattern S6 established. It points to the operating loop and handoff rules rather than to a canonical `skills/ceo/*` file (none exists for a "wake" or "route" action). It does not modify `CLAUDE.md`, `constitution/AUTHORITY.md`, `governance/*.yaml`, any executive contract, any canonical `skills/ceo/*` SKILL.md, or any product-repository file, and it changes no executive activation state.

5. **Implementation:** Two artifacts. (i) Account-level Claude skill `ceo`, built with `skill-creator`, packaged as `ceo.skill` and delivered to Gina for install into her Claude profile (lives in account settings, outside repo version control). (ii) Repo adapter `.claude/skills/ceo/SKILL.md` (117 lines), version-controlled, so `/ceo` also works in a Claude Code session opened on this repo and is portable across executors. Both carry identical content and governance boundaries, including a "Routing to executive functions" section that has the CEO classify and route only to functions whose owned areas match, respect Active/Standby/Limited activation states, invoke executives as bounded functions (never personas or autonomous agents), coordinate all cross-role handoffs through the CEO (no executive-to-executive autonomous chains), keep outputs recommendation-only under `generated/` at ceiling `CEO Review Required → CEO Recommended → Chairwoman Decision Required`, and synthesize with conflicts surfaced not resolved. No `src/`, registry, status-model, executive-contract, milestone-body, or product-repository content was changed.

6. **Evidence:** `.claude/skills/ceo/SKILL.md` (repo adapter); the delivered `ceo.skill` account-skill package (not in repo); this record. The `.gitignore` continues to track `.claude/skills/` (only `.claude/settings.local.json` is ignored), so the adapter is committed.

7. **Tests and evaluation:** No governance-invariant surface was touched (10 statuses; 7 executives with CEO/CPO/CTO Active, CMO/CBO Standby, CFO/CLO Limited; no executive may approve; output ceiling `CEO Recommended`; no automatic recommendation→approval transition), so those invariants are unaffected by construction. Live trigger behavior of `/ceo`, and the CEO routing flow it describes, have **not** yet been independently verified in a real session — same open validation status as the S6 adapters. No simulated test evidence is claimed.

8. **Results:** Both artifacts written and the account skill delivered for install; the repo adapter and this record are staged in the working tree for a native-Mac commit (bridge has no Git identity or network access). The manual wake-prompt step in `docs/OPERATING_LOOP.md` §5 now has a one-command equivalent, and Gina can ask the woken CEO to consult executive functions without separate per-executive commands.

9. **Failures / unresolved risks:** (a) `/ceo` live triggering and the routing behavior are unverified until Gina runs them in a real session — undertriggering or overtriggering is possible and would be tuned via `skill-creator` description optimization if needed. (b) The account skill lives outside repo version control, so the two copies can drift; this record and the repo adapter are the version-controlled source of truth if they ever disagree. (c) A recurring 0-byte `.git/index.lock` from the bridge mount may need to be removed natively before committing. (d) This record asserts no authority the underlying files do not already grant.
